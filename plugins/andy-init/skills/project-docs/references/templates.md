# 文件範本

> **不要照抄章節標題。** 依專案實際情況取捨——
> 空章節比沒有那個章節更糟，它會讓讀者以為那件事沒被想過。
>
> 範例用具體的句子而非 `{placeholder}`，是因為 placeholder 容易被原樣留下。

---

## docs/PRD.md

```markdown
# 產品需求

> **要做什麼、什麼算完成。** 怎麼做在 ARCHITECTURE.md，做到哪在 PROGRESS.md。
>
> 本檔描述產品需求，不是實作細節。單一 task 的做法改變不需要動這裡。

## 定位

一句話說清楚這是什麼、不是什麼。

系統要能回答哪些「現況答不了的問題」——列 2–4 個，
每一個都要是**現在真的答不了**的，而不是「做起來會很好」。

## 使用者與規模

| 項目 | 定義 |
|---|---|
| 使用者 | 誰、多少人 |
| 部署 | 自架 / SaaS / 內網 |
| 安全等級 | 需要什麼、**明確不需要什麼** |

「不需要什麼」與「需要什麼」同等重要——它擋掉後續的過度設計。

## 核心功能

依使用者感知分組，不依技術分層。每項一到兩句。

## 非目標

| 不做 | 理由 |
|---|---|

**理由欄不可省。** 沒有理由的「不做」擋不住三個月後的「要不要順便做一下」。

## 成功標準

| 面向 | 可驗證的標準 |
|---|---|

每一條都要能被一個指令或一次觀察判定真假。
「效能好」不是標準，「重複進出頁面不重打 API」是。
```

## docs/ARCHITECTURE.md

```markdown
# 架構

> 系統**怎麼實作**。要做什麼看 PRD.md，做到哪看 PROGRESS.md。
> 開發時的硬性約束在 AGENTS.md——那是「不能做什麼」，本檔是「長什麼樣」。

## 技術棧

表格。每項只寫選了什麼，理由留到最後一節。

## 部署拓撲

ASCII 圖。標出**哪些元件可以失敗而系統仍能運作**——
這比畫得漂亮重要得多。

## 分層

```
A 層   職責
  ↓
B 層   職責
```

依賴方向與**不可違反的規則**（3–5 條，多了沒人記得）。
每條規則附一句「為什麼」，否則它會在某次趕工時被繞過。

## 主要目錄

| 目錄 | 內容 |
|---|---|

## 資料模型

型別慣例（精度、單位）與核心資料表分組。
**單位慣例要寫死**——「比率一律小數」這種事沒寫下來就會混用。

## 模組

| 模組 | 職責 | 最該記住的一件事 |
|---|---|---|

第三欄是這張表的價值所在。寫不出來的模組，通常表示還不夠了解它。

## 重要技術決策

| 決策 | 選擇 | 理由 |
|---|---|---|

理由要寫**被否決的替代方案錯在哪**，不是「選了 X 因為 X 很好」。
ADR 若不多，壓成這一張表即可，不必每個決策一個檔案。

## 貫穿全系統的原則

若有一條反覆出現的判斷原則（例如「缺資料回 null 不回 0」），
寫在這裡並列出它被違反時的實際代價。
```

## docs/ROADMAP.md

```markdown
# 路線圖

> **接下來往哪走。** 高層級的階段與方向，不是 task list。
> 目前做到哪在 PROGRESS.md。

## 現況

能力清單，一行一項，前面放固定進度符號：

- ✅ 完成並驗證：只有走完 AGENTS.md「證據與完成定義」的流程才能標
- 🔄 進行中
- ⬜ 未開始
- ⛔ 暫緩：同一行寫**可觀察的重評觸發條件**，不寫「以後再說」

符號固定這四個，方便掃視與 `grep "🔄"`。

## 待補完

**已有實作但資料或驗證不足**的項目。這一節常被略過，
但它是「看起來做完了、其實不能用」的唯一記錄處。

## 可能的方向（尚未承諾）

依「使用者實際會不會用」排序，**不依技術難度**。
分近期／較遠兩組即可，不要排時程。

## 明確不做

| 項目 | 理由 |
|---|---|

與 PRD 的「非目標」不同：那是產品層級，這是技術層級的
「已經有人提過、已經決定不做」。它擋掉重複的提案。

## 更新規則

只在里程碑完成、功能增刪、優先序或方向改變時更新。
```

## docs/PROGRESS.md

**最重要的一份。** 新 session 從這裡開始。

```markdown
# 現況

> **新 session 從這裡開始。**
> 要做什麼 → PRD.md｜怎麼做 → ARCHITECTURE.md｜接下來 → ROADMAP.md

**最後更新：YYYY-MM-DD**

## §0 接手速覽

換 session 只讀這一節就要能開工。

- **交接狀態**：一到三句。讀者要在五秒內知道「這個專案現在是什麼狀態」。
- **驗證基準**：當前的基準數字（測試數、lint 錯誤數、關鍵指標），下次改動要拿來比差額。
  這些數字會過期，所以只放在這裡，更新時順手改，不要另開「統計」章節。
- **下一步**：編號清單 1–3 項。多於三項表示還沒想清楚優先序。
- **動手前只要讀**：列出這次工作真正需要的那幾條（AGENTS.md 的某節、某份 reference），
  其餘不用讀。

## 進度

| 項目 | 狀態 | 備註 |
|---|---|---|
| 匯入流程 | ✅ 完成並驗證 | |
| 報表匯出 | 🔄 進行中 | 卡在時區，見「阻塞中」 |
| 權限管理 | ⛔ 暫緩 | 使用者數 > 20 時重評 |

符號固定 `⬜ 未開始`／`🔄 進行中`／`✅ 完成並驗證`／`⛔ 暫緩`。
`⛔` 一定要附**可觀察的重評觸發條件**。已完成且不會再動的項目直接刪掉，交給 git。

## 阻塞中

卡住的事，以及**為什麼卡住**。
若需要使用者操作（權限、憑證、外部帳號），把指令原樣寫出來。

## 已知問題

只列**未結案**的。已結案的屬於 HISTORY.md 或直接刪掉。

## 接手前必知

下一個 session 不知道就會做錯的事：
- 使用者偏好的工作節奏
- 已定案、不要重新提案的技術選擇
- 反覆出現的原則

## 快速上手

可直接貼上執行的驗收指令。

## 更新本檔的規則

完成一段有意義的工作後更新（docs-sync hook 會在每輪有程式變更時提醒）。
只記錄：做到哪、正在做什麼、卡在哪、下一步、下一個 session 必須知道的 context。
每次更新都要改「最後更新」日期與 §0。**不要寫成工作日誌。**
```

## docs/HISTORY.md（選配）

只在**程式碼註解引用帶編號的問題**時才建立。

```markdown
# 問題記錄與開發史

> **這份文件不需要主動讀。** 閱讀時機是「程式碼註解把你導過來」。
> 現在的狀態在 PROGRESS.md。
> 本檔 append-only：**編號一旦發出就不重複使用，也不刪除**。
> 更早的完整敘事在 git（commit <hash> 之前）。

## 問題編號

### 未結案

| # | 問題 | 狀態 |
|---|---|---|

未結案的可以寫長一點，特別是**當時判斷錯在哪**。

### 已結案

| # | 問題 | 修復 |
|---|---|---|

每筆 1–3 行。保留「錯在哪、教訓是什麼」，刪掉過程敘事。

## 開發史

階段表，每階段一行。

## 反覆出現的錯誤形狀

把散在各處的教訓歸納成 2–4 類。**這一節是本檔真正的價值**——
單一問題的記錄只防止該問題重演，歸納出的形狀能防止整類問題。
```

## CLAUDE.md（只是殼）

規則一律寫在 AGENTS.md。CLAUDE.md 只負責讓 Claude Code 自動載入 AGENTS.md，
外加少數只對 Claude 有意義的設定：

```markdown
@AGENTS.md

<!-- 以下只放 Claude Code 專屬設定（例如 skill／hook 的使用說明）；規則與陷阱寫進 AGENTS.md -->
```

不要在這裡寫任何規則——同一條規則出現在兩個檔案，就一定會有一份過期。

## AGENTS.md 的文件索引段

放在 AGENTS.md 開頭，讓 Agent 知道去哪找什麼：

```markdown
## ⚠️ 開始工作前必讀

文件只有 N 份，各自回答一個問題。**新 session 從 `docs/PROGRESS.md` 開始。**

| 文件 | 回答什麼 | 什麼時候讀 |
|---|---|---|
| **`docs/PROGRESS.md`** | **現在做到哪、下一步、卡在哪** | **每次開工** |
| `docs/PRD.md` | 要做什麼、什麼算完成 | 需求有疑問時 |
| `docs/ARCHITECTURE.md` | 系統怎麼實作、為什麼這樣選 | 動到結構時 |
| `docs/ROADMAP.md` | 接下來往哪走 | 規劃新工作時 |

**不要新增其他專案管理文件。** 資訊若放得進上述任何一份，就不要開新檔。
```

第三欄「什麼時候讀」不可省——沒有它，Agent 只能每份都讀一遍，
而那正是這套結構要消除的成本。

⚠️ **這張表要與實際份數一致。** 使用者砍掉了某一份，就刪掉那一列並改掉開頭的
N，不要留指向不存在檔案的連結（砍檔後的完整清單見 `personalization.md` 第三節）。

## AGENTS.md 的工程習慣指針段

使用者的習慣是跨專案通用時，**不要把條目複製進專案 AGENTS.md**，
只在文件索引表前面留一行指針：

```markdown
> 跨專案的工程習慣與 AI 協作硬規則在 `~/.claude/AGENTS.md`
> （由 `~/.claude/CLAUDE.md` import，每個 session 自動載入）。
> **本檔只寫這個專案特有的約束**——提到具體資料表、埠號、資料源、目錄的那些。
```

理由是複製 N 份就會漂移 N 份，而且沒有任何機制會提醒你漏改了哪一個。
分類與放置方式見 `personalization.md` 第二節。
